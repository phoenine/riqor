# 测试用例写作规则

用于生成、评审或补充产品手工测试用例。

## 有效性红线

每条用例写出前先确认：

- 用户能否通过正常界面、接口或业务流程触发？
- 条件是否在真实业务中可达？
- 预期结果是否可观察、可判断？
- 是否覆盖业务风险，而不是实现细节或编译期保证？
- 是否能追溯到上游需求、风险、影响项、验收项或测试点？

禁止写：

- 防御性 guard clause、伪造请求、业务不可达状态。
- TypeScript 类型、框架绑定等编译时保证。
- 纯技术 API 参数校验，除非对应真实业务操作。
- 需要模拟后端 500、断网等异常才能触发的手工 UI 用例。
- 为凑数量保留的重复、边缘、不可执行用例。
- 在已有测试点的情况下，静默扩展测试范围或补造新的测试点。

## 覆盖边界

测试点决定“覆盖什么”；测试用例决定“怎么执行这个覆盖”。测试用例可以发现
测试点缺口，但不能静默扩展测试范围。

当上游提供测试点时：

- 用例应实例化测试点中的覆盖意图。
- 边界值、等价类、判定表规则、状态迁移等具体数据在用例层选择。
- 可追溯关系中必须记录至少一个 TP ID。Requirement、Risk、Bug、Acceptance
  等 ID 可以作为补充追溯，但不能替代 TP ID。
- Requirement 补充追溯应使用 Atomic Requirement 的 `REQ-###`，不能只写
  `REQ-SPEC-*` Artifact 或上游 Feature ID。
- 如果发现 TP 的覆盖意图不完整，写为 `Coverage Gap`，不要直接新增超出 TP
  范围的用例。

当当前 workflow 明确省略 Test Point 阶段时，才允许直接用 Requirement、Risk、
Impact、Bug 或 Acceptance 作为覆盖权威。`test-case-design` 不能自行判断需求
简单而跳过必需的 Test Analysis / Test Points 阶段。

示例：

```text
Coverage Gap: TP-003 声明 Boundary，但只覆盖最小边界，未说明最大边界或越界条件。
```

## 用例粒度

一条用例应验证一个主要业务结果。

同一业务场景中的连续操作可以保留在一条用例中；当风险、失败原因、前置状态、角色/范围、预期结果或测试入口明显不同，应拆成多条用例。

避免过碎：

```text
TC-001：输入名称
TC-002：选择范围
TC-003：点击保存
```

避免过大：

```text
TC-001：配置创建、编辑、执行、停用、删除均正常
```

如果只是数据不同且操作路径和预期结果基本相同，可以使用数据驱动或参数化描述；如果一个数据保存成功、另一个数据保存失败，通常拆开更清楚。

参数化、多组合或复杂数据场景应使用独立的 `测试数据` 字段。单一简单数据可以
直接写在操作步骤中。

示例：

```markdown
测试数据：

| 场景 | 输入值 | 说明 |
|---|---:|---|
| 最小有效值 | 10 | 下边界 |
| 普通有效值 | 100 | 有效等价类 |
| 最大有效值 | 300 | 上边界 |
```

## 预期结果

预期结果必须可观察、可判断、稳定复现。

不要写：

```text
系统正常。
数据显示正确。
保存成功。
```

应该写：

```text
保存完成后页面仍显示 Cycle Time 为 10 秒。
重新进入该配置后该值保持为 10 秒。
```

测试入口决定默认观察层：

- UI 用例默认观察可见页面状态、用户提示、持久化后的页面值或业务下游结果。
- 接口用例默认观察 HTTP 状态、响应字段、文档化错误或持久化业务状态。
- 数据 / 集成用例默认观察可查询记录、任务输出、集成 payload 或下游业务结果。

不要在 UI 用例中要求 Redis key、SQL update、React state 或私有方法调用，除非用例类型本身就是接口、数据、集成或组件级测试，且风险明确需要。

## 标题规则

标题应优先描述“要证明的业务结果”，而不是“要执行的测试动作”。
推荐结构接近：

```text
业务条件 + 业务行为 / 变化 + 可观察结果
```

不要求机械包含三部分，但应尽量让读者仅通过标题即可理解：

```text
在什么场景或条件下，针对什么业务对象，应该产生什么结果。
```

### 1. 优先描述业务结果，不写测试动作

避免使用“验证、测试、检查、评估”等词作为标题的主要谓语。标题应表达
“要证明什么”，而不是“要做什么测试”。

较弱：

```text
旧入口控制器下线验证
监控指标验证
高可用评估
回退验证
```

推荐：

```text
旧入口下线后所有服务仍通过新入口正常访问
切换新入口后请求监控和告警数据正常采集
新入口多副本运行时单实例故障不影响服务访问
新入口异常时恢复旧入口后关键服务正常访问
```

### 2. 使用业务语言，保留必要领域术语

标题应让不了解代码实现的测试人员也能理解。

不要出现：

- 代码变量名、数据库字段名、函数/类名。
- SQL、缓存 key、配置键名。
- 内部实现流程或无业务含义的技术缩写。

较弱：

```text
ignore3xRule=true 过滤验证
fetch_cycle_times 返回结果验证
```

推荐：

```text
开启三倍基线过滤后离群周期不参与基线计算
无统计匹配的机型不参与基线计算
```

基础设施、接口或运维类测试允许保留必要的产品术语，例如 Gateway、
HTTPRoute、Harbor，但标题仍应优先表达其业务或服务结果，而不是资源配置
细节。

### 3. 标题范围必须与实际覆盖一致

标题不得夸大测试范围。“全量”“全部”“完整”“无任何影响”等绝对性表述，
仅在用例实际覆盖该范围时使用。

较弱：

```text
迁移完成后全量业务回归
```

推荐：

```text
入口迁移完成后核心业务功能正常
入口迁移完成后核心业务冒烟验证
```

标题也应匹配单条用例的主要业务结果。是否拆分用例按“用例粒度”章节判断。

### 4. 必要条件变化应体现在标题中

当预期结果依赖关键条件、角色、状态或上下文时，应在标题中体现该条件。

示例：

```text
普通用户无法查看未授权区域的数据
已停用配置不再参与自动执行
Cycle Time 设置为最小允许值时可以正常保存
切换车间后不保留上一车间的班次数据
```

不要写成：

```text
权限验证
状态验证
边界值验证
切换验证
```

异常和回退场景应描述触发条件与恢复结果：

```text
新入口异常时恢复旧入口后关键服务正常访问
服务短暂不可用恢复后请求可以重新正常处理
无可用数据时页面显示空状态且不报错
```

### 5. 标题写业务规则结果，不写测试技术

测试设计方法属于 Technique，不应成为标题主体。边界、等价类、判定表、
状态迁移、参数化数据都应转成业务规则结果；Technique、Rule ID、状态迁移
ID 和具体参数值放在可追溯关系、备注或 `测试数据` 中。

| 较弱 | 更好 |
|---|---|
| `最小值边界测试` | `Cycle Time 设置为最小允许值时可以正常保存` |
| `无效等价类测试` | `Cycle Time 低于允许范围时无法保存` |
| `Rule R2 验证` | `同步条件命中一般值规则时按指定同步词更新` |
| `Enabled -> Disabled 验证` | `已启用配置停用后不再参与自动执行` |
| `Cycle Time 为 10、100、300 时保存验证` | `Cycle Time 处于允许范围内时可以正常保存` |

### 标题自检

生成标题后至少检查：

1. 不看步骤，是否能理解该用例要证明什么？
2. 标题描述的是业务结果，而不是测试动作吗？
3. 是否包含不必要的实现术语？
4. 标题范围是否与实际步骤和预期结果一致？
5. 是否只包含一个主要业务结果？
6. 条件、角色、状态或边界是否在必要时明确？
7. 是否可以去掉“验证 / 测试 / 检查 / 评估”而让标题更具体？

推荐标题通常接近：

```text
条件 + 对象 + 结果
```

示例：

```text
旧入口下线后所有服务仍通过新入口正常访问
普通用户切换至未授权区域时无法查看区域数据
配置修改后重新执行计算使用新的配置值
Cycle Time 超过最大允许值时无法保存
```

## 格式规则

- **必须先**通过 `tools/copy_template.py --template test-cases` 创建文件；禁止手写空白
  Markdown。`validate_test_cases.py` 校验模板章节（`# 测试用例`、`## 用例列表` 等）；
  Artifact ID、类型、来源与 producer phase 由 `runs/` 中的记录提供。
- 本地用例标题使用三级标题：`### TC-001：业务描述`（`TC-` + 三位数字 + 全角或半角冒号）。
- 禁止使用 `VC-01`、`VERIFY-01`、`## 用例 1` 等非 `TC-00N` 编号作为用例标题。
- `优先级`、`外部用例ID`、`用例类型`、`可追溯关系`、`前置条件`、`操作步骤`、`预期结果`、`备注` 必须清晰。
- `测试数据` 是条件字段：参数化、多组合、复杂数据场景应独立填写；单一简单
  数据可直接写在步骤中。
- 本地尚未同步到外部平台的用例统一写 `外部用例ID：未同步`，上传或同步后再替换为真实外部用例 ID。
- `用例类型` 用于后续同步和执行分组，优先使用 `功能测试` 或 `接口测试`；确有需要时可扩展为 `数据测试`、`自动化测试` 等稳定分类。
- 操作步骤和预期结果使用有序列表，必须按索引一一对应；外部平台同步要求
  `steps`、`expects`、`stepType` 长度一致。
- 备注引用上游测试点、风险、需求、Bug 或源码证据 ID；当测试点存在时，
  `可追溯关系` 必须包含 TP ID。
- 写完用例后运行 `python3 tools/validate_test_cases.py --case-file <path>`。
- 不确定内容写入覆盖缺口或待确认问题，不编造。

## 测试管理平台映射

本地用例是平台无关的权威版本。上传或更新测试管理平台时，由 Project
Profile 选择的同步 Skill 负责字段映射、预览、确认和回填；本规则不固化平台
payload。无论平台如何表示，步骤和预期结果都必须按索引一一对应。

## Bug 回归补充用例

Bug 回归的 API / 后端缺陷也要用业务语言写标题，步骤里再写具体接口或参数。

| 错误标题 | 正确标题 |
|---|---|
| `ignore3xRule=true → Cycle 数量应减少` | `开启三倍基线过滤后参与计算的周期数应减少` |
| `ignore3xRule=false 回归保护` | `未开启三倍基线过滤时周期统计结果正常` |
| `fetch_cycle_times INNER JOIN 语义` | `无统计匹配的机型不参与基线计算` |

步骤示例（标题保持业务化）：

```markdown
### TC-001：开启三倍基线过滤后参与计算的周期数应减少

优先级：P1

外部用例ID：未同步

用例类型：接口测试

可追溯关系：TP-001 / BUG-1649

前置条件：

1. 已部署包含修复的版本。
2. 测试时间范围内存在带离群周期的机型数据。

操作步骤：

1. 调用周期分析接口，关闭「周期少于三倍基线」过滤，记录各机型参与计算的周期数。
2. 再次调用同一接口，开启「周期少于三倍基线」过滤，记录各机型参与计算的周期数。

预期结果：

1. 开启过滤后的周期数不大于关闭过滤时的周期数。
2. 至少一个机型在开启过滤后周期数减少。
```

## 增量维护

- 默认增量更新已有用例：保留有效内容、编号、上游引用和已同步的外部 ID。
- 删除或重编号测试点后，必须同步更新用例备注中的引用。
- report 或执行记录引用用例时，使用稳定 ID，不使用易变标题作为唯一标识。
