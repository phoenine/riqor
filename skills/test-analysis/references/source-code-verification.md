# 源码验证检查点

用于把需求、Bug 或版本范围中的说法落到源码证据，避免只按文档或表象设计测试点。

## 基本原则

- 需求描述是意图，源码和运行证据才是实现事实。
- 不要只读前端；字段、权限、状态、计算口径常由后端服务决定。
- 不要只读 TypeScript/Java 逻辑；UI 可见性、表头、交互入口可能在模板或配置文件中。
- 字段名、i18n 文案、接口 DTO、数据库列之间要建立映射，不要直接用代码变量写测试标题。

## 必查证据

| 场景 | 检查点 |
|---|---|
| UI 行为 | 页面组件、模板、路由、权限入口、i18n 文案 |
| API 行为 | request 封装、业务 API 模块、调用点、method、query/body、响应 envelope |
| 数据口径 | DTO、实体、数据库字段、计算服务、单位/精度/默认值 |
| 状态缓存 | store、cache key、持久化、上下文切换、退出/刷新清理 |
| 跨仓库链路 | 前端调用点、网关、后端服务、公共库、数据处理服务 |

## 风险输出要求

- 每个风险要引用需求 ID、Bug ID、源码文件、commit/diff 或知识库依据之一。
- 记录 `repository_evidence`，包括 repo、文件/commit/symbol、支撑的结论。
- 对无法从源码确认的内容写为 open question 或 coverage gap，不编造。
- 测试点应覆盖业务风险、兼容性、边界、权限、数据一致性和回归影响，不只写 happy path。

## 常见陷阱

- 把 UI 可见 bug 误判为纯前端问题。
- 把编译期类型、框架绑定、guard clause 写成手工测试点。
- 只验证原 bug 是否修复，漏掉共享组件、相邻功能和历史缺陷回归。
- 用内部字段名作为测试标题，导致测试人员无法执行。
